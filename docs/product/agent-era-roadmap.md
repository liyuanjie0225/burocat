## 0. 评审前提（声明假设）

本次评审无真实运营数据（开源项目无 MAU 看板），以下假设如有偏差，评分需重算：

| # | 假设 | 依据 |
|---|------|------|
| A1 | 项目处于**开源增长期**，首要目标是差异化传播（GitHub star / 下载量 / 视频传播），其次留存 | 官网 + 多语言 README + 增长曲线图均在服务传播 |
| A2 | 开发资源 ≈ 1 人 + coding agent 辅助，单版本可消化 4~5 人周 | v5.1.1 与 agent-status 功能的实际交付节奏 |
| A3 | 装桌宠的开发者中，Claude Code 保有量 > ZCode | 2026 市场公开份额常识，无一手数据 |
| A4 | 无硬性 deadline，无合规约束 | 开源节奏 |
| A5 | 产品红线：**轻量、零外部依赖、绝不为打扰而抢焦点、本地隐私** | README 既有哲学（内存瘦身、30FPS 省电、密码防偷窥） |

> **修订（2026-11-26）**：A3 为市场假设；作者本人常用工具栈为 **ZCode + Cursor（未来可能 Codex）**，不用 Claude Code / 豆包。自用优先阶段按 [decisions.md](./decisions.md) D5–D7 执行：R6 升为第一优先、R1a-lite 挂起、Codex 调研推迟。

**赛道判断**（2026-11 调研）：桌宠正从「桌面装饰」转向 **ambient agent observability（环境化 Agent 状态感知）**。OpenAI Codex desktop pets、agentpet（监测 Claude Code/Codex/Cursor 并随编码成长）、OpenPets 均已出现。但它们都是「widget/像素宠物 + 状态浮窗」，**没有一家具备「打字动画引擎 + 皮肤系统 + OBS 直播源 + 内置 MCP」的组合**。KuroCat 的机会：**让猫把 agent 的行为具身化演出来，而不只是显示一个状态条**。

## 4. 排期决策备忘录

**核心逻辑**：开源增长期（A1），以 RICE 60% + ICE 40% 加权，双榜交叉验证；Kano 因无调研数据仅作风险标记不参与排序；产品红线（A5）作为硬约束。

**Top 3 决策理由**：
1. **R2 拟宠化** —— 唯一别人抄不走的牌：Codex pets 只有像素浮窗，agentpet 只有进度条，而 KuroCat 有全套打字动画+表情+起床气引擎，「猫替 agent 干活」是零新增资产的差异化。
2. **R1a Claude Code** —— 让 agent 功能从「ZCode 用户的彩蛋」变成「所有 agent 用户的标配」，触达放大 5 倍以上。
3. **R6 MCP 表达工具包** —— 半周工作量让 agent 用户获得「我的 AI 有了身体」的体验，与 R2 互为放大器。

**隐含假设与风险**：
- 若 A3 不成立（用户以 ZCode 为主），R1 优先级下降、R2/R6 上升
- R2 的「猫演 agent」是否真比静态 pill 更受欢迎，无调研数据支撑——上线后用 GitHub issue/官网反馈快速验证
- 单人+agent 协作的工作量估算（A2）历史准确率未知，Now 容量已留 20%+ 缓冲

**还需要补齐的东西（「还需要什么」的回答）**：
1. **Agent hooks 能力矩阵**：Claude Code / Codex / Gemini CLI 各自 hook 事件覆盖度实测表——这是 R1/R2 的技术前提
2. **本地历史数据层**：agent_status 目前内存态，是 R5/R8/R4 的共同地基
3. **用户反馈闭环**：GitHub issue 模板加「Agent 状态功能」标签 + 官网一个反馈入口，让 R2 验证有数据可依
4. **传播素材**：R2 上线时录一支「猫替 Claude Code 敲键盘」短视频——这个功能天生适合传播，README 首图/官网首屏同步替换

## 5. 上游动态：v5.1.2 已内置简化版「AI Companion」（2026-11-26 合并时发现）

upstream qianyiai 在 v5.1.2 发布了 **AI Companion**（`src/agentCompanion.ts` + `mcp.rs` 的 `POST /hook` 桥）：豆包/WorkBuddy/DeepSeek/Codex/千问/Antigravity/Claude Code 等客户端通过 HTTP 上报 `working/thinking/waiting/done/error` 状态，驱动 `.agent-bubble` 气泡 + 简单敲键（直接调 `onKeyDown`）。**与我们的 R1/R2 部分撞车**。

**我们已保有的差异化**：
- 零配置自动安装 hooks（read-merge-atomic + byte-identical 还原）vs 上游「让 AI 自己保存配置」的引导式接入
- 真实生命周期语义（每会话任务、模型、工具计数、中断检测、时长）
- 完整拟宠化演出（等待抬头看用户、撒花、叹气、哈欠、起床气、用户优先仲裁、隐私优先）——上游敲键直接写 `onKeyDown` 会污染用户优先判定，我们的 `agentStrike` 不碰 `lastAnyKeyAt/strokes`

**R1a 的含义变化**：原计划的「Claude Code 适配器」不必从零做——**把上游 companion 的 `kuro-agent-event` 事件流桥接进我们的 embodiment 状态机**（status: working/waiting/done/error → 相位映射），即可让上游已覆盖的全部客户端立刻获得完整拟宠化演出。工作量从 ~2 周降到 ~2-3 天，且天然解决两套 pill（`.agent-pill` vs `.agent-bubble`）的 UI 并存问题（可考虑统一收敛）。

> **评审后决策（2026-11-26）**：选择性同步上游 / R1a-lite 升为下一步 / companion 桥接降为可选 / 上游 PR 策略，详见 [decisions.md](./decisions.md) D1–D4。
